# 00 · 开篇：最难监控的黑盒小朋友

先说结论：**Agent 不是「会说话的接口」，而是一个每次上班都换一条路线去公司的同事。** 传统服务你给它一张地图，它每天走同一条路；Agent 每天早上看一眼天气、心情和路况，自己决定怎么走——有时候还绕了三圈，最后告诉你「到了」。

监控一个这样的同事，靠「有没有到公司」这一个指标是不够的。你得知道他走了哪条路、在哪个路口堵了 40 分钟、为什么绕圈、油钱花了多少。这就是可观测性。

::: tip 人话翻译
- **监控（Monitoring）**：回答「现在好不好」。像体温计，38.5℃ 就是发烧。
- **可观测性（Observability）**：回答「为什么不好」。像体检报告 + 病历 + 生活习惯，能追到根因。
- **Agent 可观测性**：给一个会自己拿主意的程序装上心电图、行车记录仪和账本。
:::

## 01 传统监控 vs Agent 监控，差别到底有多大 {#difference}

传统服务的世界是确定的：一个请求进来，走几个函数，访问两次数据库，返回 JSON。它的失败方式很「诚实」——超时、500、连接池耗尽，都会留下清晰的痕迹。

Agent 的世界是概率的：同一个问题问两次，第一次调了搜索工具，第二次直接凭记忆回答；第一次 3 秒答完，第二次绕了 9 轮。它甚至会在「一切正常」的情况下给你一个编得很像的答案。

<Diagram id="blackbox" />

| 维度 | 传统服务 | Agent |
| --- | --- | --- |
| 执行路径 | 固定，可画成流程图 | 每次由模型现编 |
| 失败表现 | 抛异常、返回错误码 | 常常「成功」但答错 |
| 复现难度 | 固定输入即可复现 | 同输入不同输出，要看上下文 |
| 成本结构 | CPU / 内存 / 带宽 | token + 轮次 + 工具调用，非线性 |
| 关键问题 | 「它挂了吗？」 | 「它在想什么？为什么这么贵？」 |

这就是为什么很多团队的第一版 Agent 监控，只有一行 `logger.info("done")`。上线一周后，账单和投诉会一起教育他们。

::: warning 一个真实的比例
在一个典型的多轮 Agent 里，**首次模型调用的 token 往往只占总量的 20%~35%**。剩下 65%~80% 是上下文滚雪球、工具结果回填、以及「它又试了一次」。只盯第一次调用，等于只看冰山露出水面的那一角。
:::

## 02 没有可观测性的生产 Agent 会踩哪些灾难坑 {#disasters}

<Diagram id="disasters" />

**灾难一：循环炸成本。** 工具返回了一个空数组，模型以为「再试一次就好了」，于是同一个工具被调了 37 次。你没有轮次上限、没有单任务成本上限、也没有「同工具连续调用」的告警。第二天财务来找你。

**灾难二：静默失败。** 用户问「我的退款到账了吗」，Agent 很礼貌地回答「已到账，请查收」——但退款接口其实返回了 500，模型把工具的报错当成了「已处理」。HTTP 200，任务状态 completed，看板一片绿色。

**灾难三：幻觉无法复现。** 用户截图说「它说我的订单可以退 3000」，你打开日志，只有一行「task completed」。没有输入快照、没有上下文、没有模型原话。你甚至无法判断这是不是同一个用户。

**灾难四：超时雪崩。** 一个下游工具慢了 3 秒，Agent 开始重试，重试占满了连接池，排队变长，更多任务超时。你没有分阶段耗时，只能看到「整体变慢」，于是加机器——加完更慢。

| 灾难 | 账面损失 | 真正损失 |
| --- | --- | --- |
| 循环炸成本 | 单日账单 10 倍 | 团队对成本的信任 |
| 静默失败 | 退款 / 改址出错 | 用户信任，可能还有合规风险 |
| 无法复现 | 排查 2 天 | 迭代速度 |
| 超时雪崩 | 整批任务失败 | SLO 与口碑 |

## 03 可观测性四大支柱：Traces、Metrics、Logs、Evals {#four-pillars}

<Diagram id="pillars" />

**Traces（链路）**：一次任务经过哪些环节，每层花了多久、用了什么参数、报了什么错。它是排查的「行车记录仪」。

**Metrics（指标）**：把无数条链路压成几个数字——成功率、P95 延迟、token 用量、单任务成本。它是看板的「仪表盘」。

**Logs（日志）**：结构化的事件与审计记录，回答「谁在什么时候对什么做了什么」。它是追责的「账本」。

**Evals（评估）**：质量视角的抽样打分，回答「答案对不对」。它是唯一能抓到「静默失败」的支柱。

| 支柱 | 回答的问题 | 典型工具 | 成本 |
| --- | --- | --- | --- |
| Traces | 怎么走的 | Tempo、Jaeger、Langfuse | 高（体积大） |
| Metrics | 有多糟 | Prometheus、ClickHouse | 低 |
| Logs | 发生了什么 | Loki、ELK、OpenObserve | 中 |
| Evals | 对不对 | Phoenix、Langfuse、自建 | 中（要模型花钱） |

::: tip 人话翻译
把 Agent 想成一辆网约车：
- **Trace** 是行程轨迹，能看出它是不是绕路了；
- **Metrics** 是计价器上的数字，告诉你这单赚不赚钱；
- **Logs** 是车内录音，出了纠纷能复盘；
- **Evals** 是乘客评分，只有它知道「路线没错但体验很糟」。
:::

## 04 本手册覆盖范围与问题清单 {#scope}

这本手册不教你「怎么让模型更聪明」，只教你**怎么把它看清楚**。读完你至少能独立完成这些事：

1. 给一个 Python / TypeScript Agent 埋点，产出符合 OpenTelemetry GenAI 语义约定的 span。
2. 把 LLM 调用、工具调用、记忆读写、跨 Agent 委派放进同一条 trace。
3. 设计一套指标：任务层、模型层、工具层、体验层、业务层。
4. 写出不会吵醒人的告警规则，并让告警直接带上 trace 链接。
5. 搭出六块生产看板：总览、失败、成本、工具、会话、循环异常。
6. 做采样与冷热分离，把观测成本压到营收的合理比例。
7. 用线上 trace 反哺评测集，形成「发现问题 → 修 Prompt → 验证」的闭环。

## 05 和整套生态的关系：五块拼图，一层胶水 {#ecosystem-link}

<Diagram id="eco-hub" />

这套手册属于一个完整的系列，每个站点负责一件事，而可观测性是那层把它们粘起来的胶水：

- **[better-agent](https://yuxinrun.github.io/better-agent/)**：单智能体怎么造。它产生「轮次」「工具选择」「上下文预算」这些事件。
- **[a2a-patterns](https://yuxinrun.github.io/a2a-patterns/)**：Agent 之间怎么说话。它产生「委派」「任务状态」「跨 Agent 链路」。
- **[mcp-patterns](https://yuxinrun.github.io/mcp-patterns/)**：Agent 怎么用工具。它产生「工具调用」「权限校验」「服务端耗时」。
- **[agent-memory-patterns](https://yuxinrun.github.io/agent-memory-patterns/)**：Agent 怎么记事。它产生「召回」「命中率」「上下文注入量」。
- **[llm-gateway-patterns](https://yuxinrun.github.io/llm-gateway-patterns/)**：模型怎么被安全调用。它产生「路由」「token 计量」「成本与限流」。

::: info 一个容易忽略的事实
**观测不是第六个系统，而是每个系统的出口。** 如果网关不报 token、MCP Server 不报工具耗时、记忆层不报召回命中，那么再漂亮的可观测平台也只能看到半张图。
:::

## 避坑清单 {#pitfalls}

::: warning 开篇就要避开的四个坑
1. **先买平台，后想埋点。** 平台只负责展示，字段设计错了，换三个平台也白搭。
2. **把 prompt 全文写进 span 属性。** 高基数 + 隐私风险 + 存储爆炸，三重打击。
3. **只监控「成功/失败」二值。** 你的失败率永远是 0.3%，因为 99.7% 的错都被标成了成功。
4. **观测数据只给 SRE 看。** 产品、算法、财务都该有自己的一块看板，否则预算永远批不下来。
:::

## 小结 {#recap}

- Agent 难监控，是因为它**路径不确定、失败不诚实、成本非线性**。
- 没有可观测性，线上会用四种方式收费：循环、静默失败、无法复现、超时雪崩。
- 四大支柱分工明确：Trace 看路径、Metrics 看趋势、Logs 看证据、Evals 看质量。
- 观测不是第六个系统，而是五个系统的共同出口。
