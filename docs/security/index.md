# 11 · 安全、隐私与合规

可观测平台是**公司里最危险的数据仓库**：它同时拥有用户说的话、模型的回答、工具调用的参数、以及内部服务名。

一个配置错误，它就从「排查工具」变成「数据泄露事故」。

::: tip 人话翻译
合规的本质不是「多写文档」，而是回答五个问题：
1. 存多久？（留存）
2. 存什么？（最小化）
3. 谁能看？（权限）
4. 数据在哪？（本地化）
5. 怎么证明？（审计）
:::

## 01 数据留存策略 {#retention}

<Diagram id="retention-life" />

| 数据类型 | 建议留存 | 理由 |
| --- | --- | --- |
| 原始 trace（含属性） | 15~30 天 | 排查窗口足够，成本可控 |
| 聚合指标 | 13 个月 | 同比分析、容量规划 |
| 审计日志 | 1~3 年 | 合规要求（按行业） |
| 评测样本（脱敏） | 6~12 个月 | 回归对比 |
| 含 PII 的原始内容 | 尽量不存；必须存则 ≤ 7 天 | 风险最高 |
| 错误快照 | 30~90 天 | 复现需要 |

```python
# 分层清理：先降采样，再删除，最后归档聚合结果
RULES = [
    {"age": "7d",  "action": "drop_payload",   "match": {"has_pii": True}},
    {"age": "30d", "action": "downsample",     "keep": 0.1},
    {"age": "90d", "action": "delete_traces"},
    {"age": "13mo","action": "rollup_to_daily"},
]
```

留存策略要写进代码，不要写在 Wiki 里。Wiki 会过期，job 不会。

## 02 内容脱敏与禁止入库 {#redaction}

先说「绝对不存」清单：

| 类型 | 处理 |
| --- | --- |
| API Key / Token / Cookie | 永不入库，日志里直接删除 |
| 完整 prompt / 完整回答 | 默认不存，只存 hash 与前缀 |
| 工具返回的原始数据 | 截断 + 字段白名单 |
| 用户身份证 / 银行卡 | 掩码或哈希，绝不原文 |
| 音频 / 图片原文件 | 存引用，不存内容 |

数据分级建议：

| 级别 | 例子 | 存储位置 | 访问 |
| --- | --- | --- | --- |
| L1 公开 | 模型名、耗时 | 任意 | 全员 |
| L2 内部 | 服务名、路由、错误码 | 内部平台 | 工程 |
| L3 敏感 | 用户 ID、订单号 | 加密字段 | 按需授权 |
| L4 极敏感 | 原文对话、证件号 | 不入库或强加密 | 双人审批 |

::: warning 哈希不是万能的
手机号只有 11 位，哈希空间可以被穷举。对低熵字段要用**加盐哈希或 HMAC**，盐值单独保管。
:::

## 03 多租户隔离 {#tenancy}

<Diagram id="tenant-matrix" />

隔离有三个层级，成本与安全强度递增：

| 层级 | 做法 | 隔离强度 | 成本 |
| --- | --- | --- | --- |
| 行级 | 每条记录带 `tenant.id`，查询强制过滤 | 弱（靠代码正确） | 低 |
| 表/分区级 | 每租户独立表或分区 | 中 | 中 |
| 实例级 | 独立数据库 / 独立集群 | 强 | 高 |

```sql
-- 行级隔离最容易出错的地方：忘了 WHERE
SELECT * FROM otel_spans
WHERE tenant_id = {tenant}         -- 必须由服务端注入，不能用前端传值
  AND timestamp > now() - INTERVAL 1 DAY;
```

| 必须隔离的内容 | 说明 |
| --- | --- |
| Trace 数据 | 含业务参数，泄露即事故 |
| 指标标签 | 租户维度可反推业务量 |
| 评测样本 | 跨租户混用等于数据串门 |
| 导出任务 | 导出文件最容易失控 |
| 加密密钥 | 大客户可要求独立 KMS key |

## 04 访问权限模型 {#access}

<Diagram id="access-matrix" />

| 角色 | 聚合指标 | Trace 列表 | Trace 详情 | 原始内容 | 导出 |
| --- | --- | --- | --- | --- | --- |
| 高管 | ✅ | ✅ | ❌ | ❌ | 汇总 |
| 产品 | ✅ | ✅ | ✅（脱敏） | ❌ | 受限 |
| 工程 | ✅ | ✅ | ✅ | 按需 | 受限 |
| 客服 | 当前租户 | ✅ | ✅（脱敏） | ❌ | ❌ |
| 安全审计 | ✅ | ✅ | ✅ | ✅（审批） | ✅（留痕） |
| 外部供应商 | ❌ | ❌ | 单独环境 | ❌ | ❌ |

三条硬规则：

1. **看详情要留痕**。谁在什么时候查了哪条 trace，本身就是审计数据。
2. **导出要审批**。90% 的数据泄露是从一个 CSV 开始的。
3. **权限跟着租户走**。客服不该看到其他客户的链路。

## 05 数据本地化边界 {#residency}

<Diagram id="residency-compare" />

| 方案 | 数据在哪 | 优点 | 风险 |
| --- | --- | --- | --- |
| 全自托管 | 自己机房 / VPC | 完全可控 | 运维成本高 |
| 区域 SaaS | 指定区域节点 | 省心 | 需确认子处理商 |
| 全球 SaaS | 厂商决定 | 最便宜 | 跨境合规风险 |
| 混合 | 敏感字段本地，指标上云 | 平衡 | 架构复杂 |

::: danger 三个容易被忽略的跨境点
1. **CDN 与静态资源**：看似无关，但可能记录 IP 与 UA。
2. **厂商的技术支持访问**：支持工程师远程看你的数据，算不算出境？
3. **备份与灾备**：主库在本地，备份在境外，同样构成跨境传输。
:::

选型时一定要问供应商三个问题：数据存在哪个区域？谁能访问？删除请求多久生效？

## 合规健康指标 {#board-sample}

| 指标 | 定义 | 健康线 |
| --- | --- | --- |
| PII 命中数 | 脱敏规则触发次数 | 趋势下降 |
| 超期数据量 | 超过留存期的记录数 | 0 |
| 异常访问 | 非工作时段 / 大批量查询 | 0（需告警） |
| 导出审批率 | 有审批的导出 / 全部导出 | 100% |
| 删除请求时效 | 从请求到删除完成 | < 30 天（按法规） |

## 避坑清单 {#pitfalls}

::: warning 合规落地的五个坑
1. **留存策略只写在文档里**。没人执行，等于永久保存。
2. **测试环境用生产数据**。这是最常见、也最难解释的泄露路径。
3. **权限给到「所有人可读」**。为了方便，最后变成事故。
4. **只脱敏日志，忘了 trace 属性**。`db.statement` 里可能就有手机号。
5. **备份没纳入合规范围**。删了主库，备份还在。
:::

## 小结 {#recap}

- 留存分层：原始 trace 短、聚合指标长、审计日志按法规。
- 最小化原则：密钥、原文、证件号不进观测库。
- 隔离分三级，行级最省但最依赖代码正确性。
- 权限按角色 + 租户双维度，详情查看与导出必须留痕。
- 本地化要连 CDN、支持访问、备份一起算。
- 合规指标要能证明「我们真的在执行」。
